### 5. Frontend JSX Null Checks

Both display locations use `!= null` (loose inequality) which correctly guards against both `null` and `undefined` — the right choice for an optional API field that may be absent from the JSON response or explicitly null.

**CustomerList table cell** (`CustomerManagement.jsx` around line 112):
```jsx
{customer.bc_price_multiplier != null ? (
  <span className={`... ${
    customer.bc_price_multiplier > 0
      ? 'bg-green-100 text-green-800'
      : customer.bc_price_multiplier < 0
      ? 'bg-red-100 text-red-800'
      : 'bg-gray-100 text-gray-600'
  }`}>
    {customer.bc_price_multiplier > 0 ? '+' : ''}{customer.bc_price_multiplier}%
```

- Outer `!= null` guard is correct.
- Zero-value case (neither positive nor negative) renders as gray — correct, 0% is a valid, neutral multiplier.
- The `> 0 ? '+' : ''` prefix correctly adds a `+` sign for positive values and nothing for zero or negative (negative numbers already render their own `-` sign).

### 6. Additional Observations (Non-blocking)

**bc_sync_service — `_upsert_customer` multiplier fallback chain:**
```python
multiplier = (
    bc_cust.get("priceMultiplierPercent")
    or bc_cust.get("priceMultiplier")
    or bc_cust.get("price_multiplier_percent")
)
```
This is identical to the same block in `bc_quote_service.py`. The fallback chain handles the uncertainty about the exact BC custom field name gracefully. One edge case: if BC returns a numeric value of `0` for the multiplier, the `or` chain will skip it and land on `None` because `0` is falsy. This means a 0% multiplier from BC would be stored as `NULL`. This is a known Python gotcha with `or` chains and numeric fields. Since 0% is a valid no-markup value, this could result in a display of `-` instead of `0%` in the portal. **This was not introduced in this PR** — it is identical to the pre-existing pattern in `bc_quote_service.py`, so it is a pre-existing issue and out of scope for this review.

**`isLoading` on mutations (TanStack Query v5):**
The project uses `@tanstack/react-query` v5 (`^5.62.11`). In v5, `mutation.isLoading` was renamed to `mutation.isPending`. The new `syncMutation.isLoading` references at lines 782 and 785 will always be `undefined` (falsy), meaning the spinner and "Syncing..." text will never render. However, this is **identical to the pre-existing behaviour** of `updateMutation.isLoading`, `unlinkMutation.isLoading`, `deleteMutation.isLoading`, `linkMutation.isLoading`, and `createMutation.isLoading` — all of which are already broken in the same way throughout the existing file. The new `syncMutation` is fully consistent with the existing pattern. Fixing this is out of scope for this PR.
